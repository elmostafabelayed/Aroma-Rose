## Pre-Deployment Security, Data Integrity & Production Readiness Audit

- **Audit Date:** 2026-11-05
- **Lead Auditor:** Independent Senior Software Architect & DevSecOps Lead
- **Target Application:** Aroma Rose Full-Stack E-Commerce Platform
- **Audit Mode:** Strict Read-Only Audit & Verification

---

## 1. Executive Summary

This independent pre-deployment audit evaluates the readiness of the Aroma Rose platform for production deployment following the completion of Mission 06. The objective of this verification is not to rubber-stamp previous test results, but to independently scrutinize the actual database policies, storage architecture, operational backup reliability, testing depth, and Cash on Delivery (COD) accounting mechanisms against real-world e-commerce standards in Morocco.

### Core Audit Outcomes:
1. **Database Schema & RLS Hardening:** All 11 public tables have Row-Level Security enabled. Anonymous visitors are strictly restricted at the table-grant level to reading published products, categories, and active product images. However, the RLS policy on `public.store_settings` is overly permissive (`USING (true)`), presenting an exposure risk if table grants are ever broadened.
2. **Storage Architecture Gap:** Uploaded product images are currently written directly to the local server filesystem (`public/products/uploads/`) rather than Supabase Cloud Storage. This will cause silent media loss on serverless or ephemeral container deployments (e.g. Render, Fly.io, ECS) without persistent disk mounts.
3. **Backup Operations:** Manual backup and disaster recovery drill scripts (`backup_database.sh`, `restore_database.sh`) function correctly, but **no automated scheduler (cron, systemd, or CI job) is configured**. Furthermore, `restore_database.sh` lacks safety prompts and executes `DROP DATABASE IF EXISTS` without confirmation.
4. **Browser E2E Testing Absence:** The project possesses 203 passing backend API integration assertions and 130 passing frontend unit/logic tests, but **zero real browser UI automation (Playwright/Cypress)** exists. Browser rendering, DOM interactions, and client-side navigation have only been verified manually or via Node.js HTTP mocks.
5. **COD Financial Control Risk:** Transitioning an order to `delivered` automatically marks `payment_status = 'paid'`. In Moroccan COD logistics, physical parcel delivery does not equal immediate cash collection or driver remittance. This represents a significant financial control vulnerability.

### Release Recommendation: **CONDITIONAL GO**
Controlled deployment is permitted **only** if the documented operational prerequisites (pushing migrations to the linked Supabase project, establishing automated cloud backups, providing persistent storage for media uploads, and formally accepting the automated COD collection risk) are satisfied and signed off by the business owner.

## 4. Critical Audit Checks (Checks A – E)

### CHECK A — Supabase Database Grants and RLS
- **Status:** **PASS WITH ADVISORY**
- **Evidence:**
  - `SELECT tablename, rowsecurity FROM pg_tables WHERE schemaname = 'public';` confirmed that all 11 tables (`orders`, `customers`, `audit_logs`, `product_images`, `profiles`, `order_status_history`, `inventory_movements`, `categories`, `products`, `order_items`, `store_settings`) have `rowsecurity = true`.
  - Role table grants query on `information_schema.role_table_grants` confirmed that `anon` has only `SELECT` grants on `products`, `categories`, and `product_images`.
  - Anonymous users are completely denied `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on `orders`, `customers`, `profiles`, `inventory_movements`, and `audit_logs`.
- **Advisory Finding on `store_settings`:**
  - Table `store_settings` has RLS policy: `CREATE POLICY "Allow read access to store settings" ON public.store_settings FOR SELECT USING (true);`.
  - Currently, `anon` has no table-level grant on `store_settings`, so direct PostgREST access fails with `ERROR: permission denied for table store_settings`. Public clients obtain settings exclusively via `GET /api/v1/store/settings`, which returns a sanitized projection (`SettingsService.getPublicSettings()`) that hides internal fields and the operator ID (`updated_by`).
  - **Risk:** If a future migration or administrator runs `GRANT SELECT ON ALL TABLES IN SCHEMA public TO anon;`, the policy `USING (true)` will immediately expose internal settings and administrator UUIDs to unauthenticated scrapers.

### CHECK B — Supabase Storage Security
- **Status:** **FAIL / ARCHITECTURAL GAP**
- **Evidence:**
  - Inspected `src/modules/products/products.service.ts` (`uploadProductImage`) and `src/utils/storage.ts`.
  - Image uploads via `POST /api/v1/admin/products/upload-image` write file buffers to the local disk at `public/products/uploads/` using Node's `fs.writeFileSync`.
  - Zero Supabase Storage bucket configurations, policies (`storage.objects`), or storage API calls exist in `supabase/migrations/` or application code.
  - Express serves uploaded media via `express.static(path.join(process.cwd(), 'public', 'products'))`.
- **Operational Impact:**
  - In a modern containerized or serverless deployment where the filesystem is ephemeral, images uploaded by staff will vanish upon container restart or redeployment.
  - If Supabase Cloud Storage is required, a bucket named `catalog` must be created with explicit storage RLS policies, and `uploadProductImage` must be refactored to upload via `@supabase/storage-js`.

### CHECK C — Backup and Restore Reliability
- **Status:** **PARTIAL**
- **Evidence:**
  - `scripts/backup_database.sh` executes `pg_dump`, compresses with `gzip -9`, verifies archive integrity via `gzip -t`, and applies a 30-day retention prune.
  - `scripts/restore_database.sh` restores an archive into a temporary test database, suspends triggers during import (`SET session_replication_role = 'replica';`), verifies table/record counts, and cleans up.
  - Verified restore drill against a real dump with 11 tables and 0 constraint errors.
- **Identified Deficiencies:**
  1. **Zero Automation:** No cron jobs, systemd timers, or scheduled CI workflows exist. Backups are entirely manual.
  2. **Destructive Restore Script Risk:** `restore_database.sh` executes `DROP DATABASE IF EXISTS ${TARGET_DB};` without interactive confirmation (`Are you sure? [y/N]`). If executed with a production database name by accident, data loss is instantaneous.

### CHECK D — Browser-Level End-to-End Testing
- **Status:** **NOT VERIFIED / NOT IMPLEMENTED**
- **Evidence:**
  - Searched `package.json` and `frontend/package.json` for `playwright`, `cypress`, `puppeteer`, and `selenium`. Found 0 browser testing tools.
  - Test suites execute exclusively in headless Node.js runtimes:
    - `tests/api/runner.ts` uses `fetch` to test HTTP API responses.
    - `frontend/tests/*.test.ts` uses `tsx --test` to test business logic functions, formatting utils, and Zod schemas.
- **Audit Conclusion:**
  - True browser UI execution (DOM rendering, responsive reflow, CSS transitions, client-side routing edge cases) has **not been tested via automated browser tooling**.
  - While API coverage is thorough (15 suites, 203 assertions), HTTP testing must not be conflated with real browser E2E verification.

### CHECK E — COD Payment Collection Integrity
- **Status:** **FAIL / FINANCIAL CONTROL RISK**
- **Evidence:**
  - Inspected `src/modules/orders/orders.service.ts` line 529–538:
    ```sql
    UPDATE public.orders
    SET status = $1::order_status,
        payment_status = CASE
          WHEN $1::order_status = 'delivered'::order_status AND payment_method = 'cod' THEN 'paid'::payment_status
          ELSE payment_status
        END,
        updated_at = now()
    WHERE id = $2
    ```
  - Transitioning an order to `status = 'delivered'` automatically sets `payment_status = 'paid'`.
- **Financial Control Flaw:**
  - In Moroccan Cash-on-Delivery logistics, delivery confirmation and courier cash remittance are distinct operational events. Couriers frequently remit funds in weekly batches, partial payments occur, and parcel losses/disputes happen after delivery marks.
  - The application lacks a dedicated **cash reconciliation workflow** (e.g. `POST /api/v1/admin/orders/:id/reconcile-payment`).
  - Consequently, executive dashboards and reports count orders as `collected_revenue` the moment they are marked `delivered`, even if the physical cash has not reached the merchant's bank account.

## 10. Prioritized Remediation Plan

### Pre-Deployment (Must Complete Before Launch):
1. **Apply Migrations to Supabase Cloud:**
   Execute `npx supabase db push --remote` to provision the 11 tables and RLS policies on `tmzedtqltmtjubdguybe`.
2. **Seed Initial Catalog:**
   Execute catalog seed on the remote cloud database to populate 72 items and 6 botanical categories.
3. **Provision Persistent Upload Storage:**
   If deploying containerized on Render/Fly.io, attach a persistent volume to `/public/products/uploads` OR switch to Supabase Storage.
4. **Configure Automated Backups:**
   Enable Point-In-Time Recovery (PITR) in Supabase Dashboard (Project Settings $\rightarrow$ Database $\rightarrow$ Backups).

### Post-Deployment (Phase 2 Improvements):
1. **Implement COD Cash Reconciliation:**
   Decouple physical delivery (`status = 'delivered'`) from payment collection (`payment_status = 'paid'`), adding an admin cash remittance screen for delivery receipts.
2. **Add Playwright Browser Automation:**
   Implement end-to-end browser test suites covering cart checkout and admin login.
3. **Harden `store_settings` RLS Policy:**
   Restrict `store_settings` SELECT policy to `fn_is_admin_or_staff()`.

## 11. Final Release Decision

# **DECISION: CONDITIONAL GO**

### Justification:
The platform's core application code, database constraints, input sanitization, and financial reporting formulas are technically robust, thoroughly tested, and free from critical remote code execution, SQL injection, or unauthenticated data leak vulnerabilities.

However, deployment cannot proceed unconditionally due to:
1. Pending migration application on the linked remote Supabase project.
2. The operational risk of local disk storage for image uploads on ephemeral hosts.
3. The business risk of automated COD cash collection marking upon delivery.

Controlled production release is approved upon formal acceptance of the pre-deployment items detailed in Section 10.
